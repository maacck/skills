完成标准

  • 管理员首页的三个组件（近 7 日登录人数、近 30 天打开次数最多的 5 个应用、近 7 日每日活跃人数）各自只发一个 POST /api/admin/analytics/query，数据来自真实表
  • 在真实 Launchpad 上点开一个应用后，「前 5 应用」的计数加一
  • pytest 中同一批固定数据得到确定的数字，包括 UTC+8 的日界

要点 At a Glance

查询形式用 JSON 语义查询，不用类 SQL。

服务端用 SQLAlchemy 白名单编译。

类 SQL 文本查询：要写解析器，攻击面更大，TS 也拿不到类型，而且最后同样要白名单。

应用使用量要新增数据。

Launchpad 经 GET /api/launchpad/{id}/open 跳转并写 application_launch 表。

前端打点（beacon），会在页面跳走时丢数据。

按天分桶需要时区。

服务端在 Python 里算好每个桶的 UTC 边界再查询。

按 UTC 分桶会把北京时间 0–8 点算进前一天。

最弱的一环：打开记录的前置工作。

一次查询怎么走

前端只发一个 POST /api/admin/analytics/query；权限、校验、分桶都在服务端完成。

查询结构：properties 与 metrics ADR-7

properties 是不聚合的分组列，metrics 是聚合列；字段能做什么由目录决定。

时区分桶 ADR-4

数据库只存 UTC，「一天」取决于查看者所在时区；服务端按请求的时区切出 UTC 边界再查询。

应用打开怎么记录 ADR-3

指标的含义是「经过 Portal 入口的打开请求」：直接收藏应用网址的访问不计入。

前置：生产 Launchpad 接真实接口

生产 Launchpad 改为读取已有的 GET /api/launchpad（真实 UUID、kind、url、icon、分类），mock 只留给 Storybook。

只把卡片链接换成 /open 时 ID 不是 UUID，打不开也记不到（Blindspots）。

风险 pre-mortem

风险影响缓解
某个查询扫过一整年审计，拖慢数据库管理端变慢，登录也可能受影响按粒度限制时间范围；实测 365 天约 2.7 s，只在管理端、且不常用；超出 ADR-2 预算就做预聚合
时区桶有错位（夏令时、跨月）图上日期错一天边界计算是纯函数，单测覆盖 Asia/Shanghai、America/New_York 的夏令时切换日和月末
漏校验字段，前端能按任意列分组越权读个人信息Pydantic 用 Literal 限定数据集字段，编译器只认目录里的列和角色；测试覆盖未知字段、user_id 作 property、对 enum 求 sum 都返回 422
avg 在 PostgreSQL 上返回 Decimal，JSON 序列化成字符串前端图表拿到字符串编译器对 avg 结果统一转成 float；测试断言 JSON 中是数字
跳转端点被当成开放重定向钓鱼只跳到该应用登记的 URL；没有权限或应用已停用时返回 404
「活跃」定义和管理员的直觉不一致数字被质疑在目录和界面提示里写明口径；开放问题 1
应用打开记录无限增长存储保留 400 天，CLI 清理命令沿用 sso-purge 的做法，测试覆盖边界两侧
接真实 Launchpad 时改坏现有行为（分类标签、按类型筛选、新标签页）员工打不开应用现有 Launchpad 故事和 play 测试改用真实形状的数据后全部保留；手工点开 sso 和 link 各一个

约束

1. 「活跃用户」怎么算？

登录成功 + 应用内 SSO 登录 + 打开应用（2026-11-11）

当天至少有一次登录成功、应用内 SSO 登录或从 Launchpad 打开应用；changes: active_users 数据集里合并哪些事件。

2. 谁能看统计？

只有管理员和 Owner，只看聚合；changes: 路由位置、是否允许按用户分组、隐私说明。

3. 应用打开记录保留多久？

400 天，加 CLI 清理命令（2026-11-11）

400 天（能做同比），加 bedrock run 清理命令；changes: 是否需要清理任务，以及能否做年度对比。

盲点10 条
发现类型为什么会出问题落在
应用打开次数在服务端没有数据；生产 Launchpad 用 mock 应用（字符串 ID 如 gitlab），没有接 GET /api/launchpad（app/(launchpad)/page.tsx:4，launchpad-view.tsx:40-45）missing concept「前 5 应用」无从统计；只把卡片链接换成 /open 时 ID 不是 UUID，打不开也记不到ADR-3、Roadmap 2
未知用户的登录失败没有 subject_user_id（identity/signin.py:129）landminesign_ins 上 count_distinct(user_id) 只统计能认出的人，和 count 不是同一口径数据集目录说明
命名的 FROM (VALUES …) AS name(cols) 是 PostgreSQL 写法；values(...).data(...).cte() 才可移植（SQLAlchemy 2.1 sql/_selectable_constructors.py:787-825）convention写成子查询形式就破坏可移植性ADR-4
登录方式和失败原因只在 audit_record.details（JSON）里；ADR 0005 写明「V1 没有查询会搜 JSON 列」convention按方式分组就要读 JSON，等于修改 ADR 0005 的那条结论ADR-5
会话在 Redis，没有历史；last_sign_in_at 被覆盖landmine「活跃人数」不能按会话算，只能按事件算Open Question 1
没有组织时区设置；前端按浏览器时区算日界（lib/admin-api.ts dayStart()）convention后端按 UTC 分桶会和管理员看到的日期差 8 小时ADR-4
require_administrator 已挂在 /api/admin 路由上（api/routers/admin/__init__.py:17）prior art权限不必另写ADR-6
列表接口已有 {field, op, value} / {and: [...]} 筛选格式（docs/developer/admin-api.md:46）prior art自创一种筛选格式就成了第二套约定ADR-1
CSRF 由中间件按 Origin 检查（api/middleware.py:1）convention用 POST 传查询体不需要额外处理ADR-1
审计没有 (outcome, occurred_at) 索引landmine可以先按 event_type 索引缩小范围再筛 outcome，现有规模没问题；之后规模大了才需要预聚合Risk
